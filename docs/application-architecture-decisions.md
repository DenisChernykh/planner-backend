# Группировка application и фабрики сценариев

Решение от 8 октября 2026 года по issues #12 и #13. Основой служит текущий
workspace: один Worker, HTTP, Telegram webhook и существующий минутный Cron.

## Файлы и папки

Файл выделяется, когда у определения есть самостоятельная обязанность, независимый
контракт или отдельная причина измениться. Папка объединяет несколько сценариев
одной операции продукта: `entries`, `settings`, `sessions`, `delivery`.
Число строк или одинаковый набор папок во всех модулях не служат критерием.

Связанные входные типы, небольшие функции и политики можно хранить рядом со
сценарием, если они используются только им. Общий тип выделяется, когда его
потребляют несколько сценариев или адаптеров; общий порт остаётся в `ports`.
Чистая продуктовая политика остаётся в `domain`, координация чтения и записи —
в `application`, HTTP DTO — в `presentation`. Маленькой возможности достаточно
плоской структуры.

Конкретные варианты оценены так:

- В Notes сохраняются `reading/list-notes.query.ts`, `reading/get-note.query.ts`
  и отдельные операции записи. При разборе чужого `noteId` путь короткий:
  контроллер → GetNoteQuery → owner-scoped порт → доменная ошибка → HTTP 404.
  Объединение чтения и записи в общий сервис заставит читателя просматривать
  нерелевантные ветки и соединит разные контракты. Небольшой размер этих файлов
  сам по себе не оправдывает объединение.
- В IdentityAccess модели входа/сессии и их политики остаются рядом внутри
  соответствующих папок. Изменение срока сессии требует читать `session-policy`
  и сценарий аутентификации; протокол OIDC при этом не попадает в этот путь.
  Если одно определение окажется нужно только одному сценарию, его можно перенести
  в тот же файл. Сейчас модели нужны портам и нескольким сценариям, поэтому их
  объединение со всеми login/use case увеличит область чтения.
- В Reminders форматирование сводки выделено в `delivery/format-digest.ts`:
  вход — цели, дата и прежние идентификаторы; выход — сообщение и стабильные
  идентификаторы кнопок. Читатель может проверить ограничение 30 и индексы без
  БД и транспорта. `DigestMessages.prepareDelivery` явно сохраняет payload,
  `refreshAfterAnswer` явно редактирует доставленное сообщение. Объединение этих
  операций с форматтером скрывало побочные эффекты.
- `application/reports/progress-reports.ts` уже группирует тесно связанные
  операции отчётов. Не дробим их механически на класс для каждого метода:
  отдельный сценарий потребуется при появлении самостоятельного контракта
  или существенно иной зависимости.

Структурные `Pick<UseCase, "execute">` применяются там, где контроллер/сценарий
нуждается только в этой операции. Они сохраняют типы аргумента и результата и
позволяют подставить fake без приватных полей класса. Общий базовый UseCase,
DI-контейнер и дополнительные слои для симметрии не вводятся.

## Потребители фабрик

| Потребитель | Нужные операции |
| --- | --- |
| Planning HTTP | План, корзина, создание/изменение/порядок/удаление/восстановление целей; снимки, сохранение, корректировка и удаление результатов |
| Search HTTP | Planning search и подготовка текущего месячного плана |
| Progress HTTP | Planning progressSources, настройки начала учёта и расчёт прогресса |
| Reminders HTTP | Подготовка текущего плана; состояние связи, общие настройки и правила целей; подключение/отключение; настройки и предпросмотр отчётов |
| Telegram webhook | Проверка и подтверждение связи, получение чата, отключение, обработка ответов/кнопок; открытие и доставка вопросов, сохранение результата, обновление сводки |
| Минутный Cron | Восстановление доставок, подготовка текущего плана, продвижение расписаний, доставка напоминаний и отчётов |
| Часовое обслуживание внутри того же Cron | Planning pruneEntryCommands; Reminders retention заданий и просроченных link tokens |

Сохраняем `createPlanningUseCases`, `createPlanningOperations` и
`createReminderOperations` как небольшие фабрики без I/O. Сценарии и адаптеры
создаются синхронно внутри корня модуля, запросы выполняются только при вызове
операции. PlanningOperations предоставляет узкий межмодульный контракт; HTTP
использует свои use case. Reminders имеет общий граф доставки, вопросов, ответов
и отчётов: его разделение сейчас продублирует сборку этого графа и расширит
публичную поверхность. Конструкторы не читают БД и не отправляют сообщения.

Для нового обслуживания команд выделена только `createPlanningMaintenance`:
composition root вызывает владельца таблицы, не создаёт полный HTTP/бот граф и
не передаёт его Reminders. Это разделение объясняется явной обязанностью и
владением данными. Ускорение холодного старта или экономия CPU не заявляются:
измерений производительности фабрик нет.

Будущее разделение Reminders оправдано, если группы получат независимый жизненный
цикл или для чтения простых HTTP настроек потребуется создавать адаптер с I/O.
В таком случае общий граф остаётся приватным helper корня, а публичные фабрики
показывают нужную потребителю группу. Сборка не переносится в контроллеры;
ownerId передаётся каждой операции, пользовательские данные не хранятся в
долгоживущих экземплярах.

## Владение D1

| Модуль | Таблицы |
| --- | --- |
| IdentityAccess | users, external_identities, sessions, chatgpt_connections |
| Notes | notes |
| Planning | plan_goals, plan_month_rollovers, goal_entries, planning_entry_commands |
| Progress | progress_settings |
| Reminders | reminder_settings, goal_reminders, telegram_links, telegram_link_tokens, reminder_jobs, progress_report_settings, goal_progress_reports |

Механическая центральная Drizzle schema сохраняется. Адаптеры могут читать
соседние таблицы в owner-scoped JOIN/EXISTS для атомарной проверки активности
цели; изменение чужой таблицы требует публичной операции владельца. Единственное
существующее исключение записи явно закреплено в gate:
`D1ProgressReportRepository.save` атомарно сохраняет общую дату начала учёта в
`progress_settings` вместе с настройками отчётов. Новые адаптеры не получают это
исключение автоматически.

Проверка границ запрещает application → корень другого модуля с исполняемым
wiring; доступны только `public-contracts.ts`. Она распознаёт известные таблицы
в SQL INSERT/UPDATE/DELETE и Drizzle insert/update/delete, включая попытку удалить
квитанции Planning из Reminders. Регрессионные fixture-тесты проверяют нарушения,
разрешённый контракт и чтение JOIN. Это статическая проверка распространённых
форм кода, а не доказательство для произвольно построенного динамического SQL.
